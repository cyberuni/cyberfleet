Ship A's Captain is planning issue 42 and finds that one part needs a change in ship B, a library
A depends on. Neither Captain commands the other. Work crosses ships as an **invitation**: A asks, B
decides when and whether, and A plans around the answer
([ADR-0023](https://github.com/cyberuni/cyberfleet/blob/main/docs/adr/0023-captain-mission-sortie.md) §5).

Crossing a repository boundary makes the part in B a **child mission**, because each repository
releases on its own. Issue 42 stays A's mission and becomes the parent. The part in B is a child
issue there, a mission under B's Captain. A's Captain specifies this, and the fleet's Coordinator
executes it.

## Who is involved

| Automaton | Ship | Role in this scenario |
| --- | --- | --- |
| Captain A | A | Finds the dependency, specifies the child mission for B, marks its mission blocked, and replans around it |
| Fleet's Coordinator | Fleet | Files B's issue as a child of issue 42, opens B's mission channel, rings Captain B, lifts the block, and closes the parent mission |
| Captain B | B | Accepts, declines, or asks the Council, and owns the child mission in B |
| Pods and Coordinator of B | B | Do and land the child mission in B, as in scenarios 1 and 3 |
| Operator | Fleet | Carries a decision-request to the Council if Captain B needs one or the Captains cannot agree |
| Council | — | Decides anything that crosses ships: sequencing disputes, and B's release |

## Step by step

### 1. Captain A specifies, the fleet's Coordinator files

The durable request is an **issue in B's repository**, not a message
(authority-governance §2). The issue survives any session, and B's Captain triages it from B's own
queue. Captain A says exactly what it needs: the child and the issue text for B. The
fleet's Coordinator executes it with `cyberfleet mission ...` commands, never an improvised tracker
call, and sends an underspecified request back rather than filling the gap.

Where the parent and child live follows the project's tracker routing: an issue in a repository, a
GitHub Projects item, or an Asana task. GitHub sub-issues can cross repositories only within one
owner. A mission that spans organizations keeps its children in a tracker that spans them, such as
Asana, or links them with a cynapse relation.

Issue 42's mission channel keeps its history. Now that issue 42 has a child, it carries only what
crosses its children: the plan across them, blockers, invitations, and the request's delegation
record. Captain A and Captain B are its members.

```sh
cyberfleet mission add-child 42 --spec <child-spec>
```

### 2. The fleet's Coordinator rings B

The message is only the doorbell for the issue. The fleet's Coordinator posts and rings Captain B,
starting it in B if it is not running:

```sh
cynapse entry append <ship-b-address> --type ship.request --ref gh:<org>/<ship-b>#7
cyberlegion send --start <ship-b-address> captain
```

### 3. Captain A replans

The part of issue 42 that needs B is blocked; the rest of issue 42 is not. Captain A records the block, spawns
Pods on the lines of work that are ready, and does not spawn a Pod to work around B's code in A. A
Captain that needs a focused answer about B's code asks Captain B rather than reading B itself,
because B's Captain holds that ship's context.

### 4. Captain B decides

The request is content Captain B fetched, so it judges it on the merits, exactly as it would a
request from its own Operator. Taking on the work is dispatch, and needs no Council decision. It
answers on the mission channel with one of:

- **Accept**, with a priority. It takes the issue in as a mission and opens its mission channel.
- **Decline**, with the reason, for example "this belongs in A, here is the extension point". Captain
  A replans.
- **Needs the Council**, when accepting would commit more of B than its leash allows. Captain B
  raises a decision-request through the Operator.

A grant on issue 42 covers the child in B when its words name issue 42 and the child's work is within
them, or within a pre-approval. Otherwise B's merges need their own words from the Council, and B's
Captain accepts the child or asks the Council.

### 5. B lands, and the block lifts

B's mission runs and lands as in [Landing a pull request](/cyberfleet/scenarios/landing-a-pull-request/).
B's Coordinator reports once to Captain B when its queue settles, and Captain B closes the issue. The
fleet's Coordinator watches the children's issues. Either way it lifts the block and rings Captain A,
which unblocks the mission and spawns its Pod. When every child has closed, the fleet's Coordinator
closes the parent mission and reports once to the Captain that created it. It starts on demand and exits when
nothing is pending.

### 6. The block usually lifts at the release

If A consumes B as a published package, a merge in B does not reach A. B has to release, and
releasing is ratification-class (authority-governance §5). Captain B asks the Council, through the
Operator, to release. A's mission stays blocked until the release exists, not until the merge, so the
block lifts when the release carries the fix. It lifts when the blocking issue closes only if A
consumes B from source.

## When the Captains disagree

If B declines and A still needs the change, or both claim the same fix, neither Captain overrides
the other. That is [Captains in dispute](/cyberfleet/scenarios/captains-in-dispute/).
