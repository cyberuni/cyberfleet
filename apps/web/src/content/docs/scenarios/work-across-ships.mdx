Ship A's Captain is planning issue 42 and finds that one part needs a change in ship B, a library
A depends on. Neither Captain commands the other. Work crosses ships as an **invitation**: A asks, B
decides when and whether, and A plans around the answer
([ADR-0023](https://github.com/cyberuni/cyberfleet/blob/main/docs/adr/0023-captain-mission-sortie.md) §5).

The part in B is a **dependency**: a mission in B that **blocks** issue 42, because each repository
releases on its own. Issue 42 stays A's mission and is *blocked by* the new one. The mission in B
belongs to B's Captain, who holds its issue. A's Captain specifies it, A's Coordinator files it in B,
and A's Captain writes the blocking link.

## Who is involved

| Automaton | Ship | Role in this scenario |
| --- | --- | --- |
| Captain A | A | Finds the dependency, specifies it for B, writes the blocking link, opens B's mission channel and mentions Captain B, replans around it, and lifts the link when the fix lands |
| Coordinator A | A | Files B's issue from A's ship queue, and posts to the queue when the fix lands |
| Captain B | B | Accepts, declines, or asks the Council, and owns the mission in B |
| Pods and Coordinator of B | B | Do and land the mission in B, as in scenarios 1 and 3 |
| Operator | Fleet | Carries a decision-request to the Council if Captain B needs one or the Captains cannot agree |
| Council | — | Decides anything that crosses ships: sequencing disputes, and B's release |

## Step by step

### 1. Captain A specifies, its Coordinator files

The durable request is an **issue in B's repository**, not a message
(authority-governance §2). The issue survives any session, and B's Captain triages it from B's own
queue. Captain A says exactly what it needs: the dependency and the issue text for B. It posts that
to A's ship queue as tracker mechanics. Coordinator A executes it with `cyberfleet mission ...`
commands, never an improvised tracker call, and sends an underspecified request back rather than
filling the gap. It files the issue and posts the reference back in the queue thread.

Where the two missions live follows the project's tracker routing: an issue in a repository, a
GitHub Projects item, or an Asana task. The blocking link has one home per ship, set in that
routing: the tracker where it supports links across owners, such as Asana, otherwise a cynapse
state record. Only Captain A writes it, checking its lease first.

```sh
cyberfleet mission block 42 --on gh:<org>/<ship-b>#7
```

### 2. Captain A opens B's mission

The issue is the durable request. The mission channel is the invitation. Captain A brings the work,
so it creates the mission channel, keyed by B's issue, posts the request as its first entry, and
mentions Captain B. A request needs an answer, so the mention starts Captain B through its lease if
no session is acting as it. The channel's members are Captain A and Captain B.

```sh
cynapse channel create <handle> --kind work --type gh.issue --title "<title>" \
  --store gh --native-id <ship-b-issue-node-id> --member <ship-a>/captain --member <ship-b>/captain
cynapse entry append <ship-b-mission-channel> --ref gh:<org>/<ship-b>#7 --body "@<ship-b>/captain <the request>"
```

### 3. Captain A replans

The part of issue 42 that needs B is blocked; the rest of issue 42 is not. Captain A calls the
frontier command, which excludes the blocked work, and spawns Pods on the lines of work that are
ready. It does not spawn a Pod to work around B's code in A. A Captain that needs a focused answer
about B's code asks Captain B rather than reading B itself, because B's Captain holds that ship's
context.

### 4. Captain B decides

The request is content Captain B fetched, so it judges it on the merits, exactly as it would a
request from its own Operator. Taking on the work is dispatch, and needs no Council decision. It
answers on B's mission channel with one of:

- **Accept**, with a priority. The issue is B's own mission, and B's Captain takes it in.
- **Decline**, with the reason, for example "this belongs in A, here is the extension point". Captain
  A replans.
- **Needs the Council**, when accepting would commit more of B than its leash allows. Captain B
  raises a decision-request through the Operator.

A grant on issue 42 does not cover the mission in B. It needs the Council's words naming it, or a
pre-approval such as "any fix #42 needs in B". Otherwise B's merges wait for the Council's words, and
B's Captain accepts the mission or asks the Council. To grant once over the whole effort, make it a
mission with sub-missions.

### 5. B lands, and the block lifts

B's mission runs and lands as in [Landing a pull request](/cyberfleet/scenarios/landing-a-pull-request/).
B's Coordinator reports once to Captain B when its queue settles, and Captain B closes the issue.
Coordinator A watches for the fix and posts to A's ship queue when it lands. Captain A lifts the
blocking link, calls the frontier command again, and spawns its Pod. Captain A closes issue 42, as
the holder of that issue. Coordinator A starts on demand and exits when nothing is pending.

### 6. The block usually lifts at the release

If A consumes B as a published package, a merge in B does not reach A. B has to release, and
releasing is ratification-class (authority-governance §5). Captain B asks the Council, through the
Operator, to release. A's mission stays blocked until the release exists, not until the merge, so
Coordinator A posts to the queue, and Captain A lifts the link, when the release carries the fix. It
happens when the blocking issue closes only if A consumes B from source.

## When the Captains disagree

If B declines and A still needs the change, or both claim the same fix, neither Captain overrides
the other. That is [Captains in dispute](/cyberfleet/scenarios/captains-in-dispute/).
