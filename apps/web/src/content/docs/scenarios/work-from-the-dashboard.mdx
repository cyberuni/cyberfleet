You are in a ship's Dashboard tab, talking to its Operator, and you ask for a change: "Add retry
with backoff to the uploader." This page follows that request until the work is on trunk.

## Who is involved

| Automaton | Tier | Role in this scenario |
| --- | --- | --- |
| Council | Human | Asks for the work, and later answers the merge announcement |
| Operator | Sonnet | Takes the request, relays it, and reports back |
| Captain | Opus | Judges the request, writes the issue and the plan, and spawns Pods |
| Pod | Set by the Captain | Does the work in a worktree and opens the pull request |
| Coordinator | Haiku | Lands the pull request. See [Landing a pull request](/cyberfleet/scenarios/landing-a-pull-request/) |

## Step by step

### 1. The Council asks

Your message is a turn in the Operator's session, so it is an order
([authority-governance](https://github.com/cyberuni/cyberfleet/blob/main/packages/cyberfleet/skills/authority-governance/SKILL.md) §1).
The Operator first decides what kind of turn it is:

- **A question** ("what's open?", "is PR 57 green?") the Operator answers itself, from the status
  UI's sources: `cyberfleet missions`, `gh`, and the ship's channels. The Captain is not woken.
- **Work**, as here, goes to the Captain. The Operator does not judge priority or scope itself.

Because this order dispatches work, the Operator also announces the clean bar and asks whether to
merge each resulting pull request once it is clean. Your reply is the standing merge delegation
(authority-governance §7). The Operator records your words, as you wrote them, on the work channel
when one exists, and sends them to the Coordinator as a turn.

### 2. The Operator relays to the Captain

The Operator posts and rings: it posts the request to the ship's address channel, starts the
Captain if no healthy one holds the lease, and rings it.

```sh
cynapse entry append <ship-address> --type ship.request --body "<the Council's words>"
cyberlegion service start <project> captain --agent captain --model opus
cyberlegion unit nudge <captain-handle>
```

`service start` either returns the live Captain or starts exactly one, even when two callers race.
The Operator then waits for the reply on the request's thread with `cynapse entry wait <entry>`.

### 3. The Captain judges the request

The Captain reads its address channel (`cynapse entry list <ship-address> --unread`) and judges the
request on three points:

- **Freshness.** Is it already tracked, already done, or stale? It searches the tracker
  (`gh issue list --search`) and resolves any existing work channel
  (`cynapse channel resolve --store gh --native-id <id>`).
- **Priority.** Where does it sit against the open plan? This is where the Opus tier earns its cost.
- **Details.** Scope, acceptance, and how to split it into sorties.

It then creates or updates the issue (`gh issue create` or `gh issue edit`), opens the issue's work
channel, and adds the sorties to the ship's mission graph as its single writer.

```sh
cynapse channel create <handle> --kind work --type gh.issue --title "<title>" \
  --store gh --native-id <issue-node-id> --member <captain>:lead
```

### 4. The Captain spawns Pods

For each sortie on the ready frontier, the Captain spawns a Pod into its own worktree, choosing the
Pod's model for the sortie:

```sh
cyberlegion spawn --agent pod --model sonnet --branch <sortie-branch> --base main \
  --brief-file <brief> --at workspace
```

The brief names the work channel, so the Pod reports there, and names the Coordinator's address, so
it knows where to say its pull request is ready.

### 5. The Captain replies, and the Operator reports

The Captain replies on the request's thread with the issue, its priority, and the Pods it spawned.
The Operator's `entry wait` returns, and it tells you in a sentence. After that, the Captain
has nothing to do until something needs a decision, so its session can idle or exit.

### 6. Pods work, and hand off to the Coordinator

Each Pod works in its worktree, opens a pull request, and shepherds it as it does today. When it
is done, it reports on the work channel and tells the Coordinator, starting it if needed:

```sh
cynapse entry append <work-channel> --type pod.report --ref gh:<org>/<repo>#57
cynapse entry send <coordinator> --type pr.ready --ref gh:<org>/<repo>#57
cyberlegion service start <project> coordinator --agent coordinator --model haiku
cyberlegion unit nudge <coordinator-handle>
```

From here the work is landed as described in
[Landing a pull request](/cyberfleet/scenarios/landing-a-pull-request/).

## What changes from ADR-0023

- **The Operator lives in the ship.** ADR-0023's Operator was reached from any session. Here each
  ship has its own Operator in its Dashboard tab, and the fleet-level Operator is
  [the Command Center's](/cyberfleet/scenarios/work-from-the-command-center/).
- **The Captain no longer lands work.** ADR-0023 gives the Captain trunk, merge order, and
  retirement. Here the Coordinator lands, and the Captain keeps the plan, the tracker, and the
  decisions.
- **Model tiers are part of the design.** Each role names its tier, and `service start` passes it
  through.
