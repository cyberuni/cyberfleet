Every scenario that produces code ends here. A Pod has opened a pull request and told the
Coordinator it is ready, as a thread in the ship's queue. The Coordinator's job is to get it onto
trunk in the right order without breaking trunk, to mention the Captain at once only when a decision
is needed, and otherwise to report once, when its queue settles.

## Who is involved

| Automaton | Tier | Role in this scenario |
| --- | --- | --- |
| Pod | Set by the Captain | Rebases, fixes, and re-verifies its own pull request when told |
| Coordinator | Haiku | Works from the ship queue: applies the clean bar, orders rebases, merges, escalates, and reports once. Joins no mission channel |
| Captain | Opus | Rules on escalations, then reviews the settled queue: closes or reopens issues and replans |
| Council | Human | Holds merge authority, and decides anything above the Captain's leash |

## Why a separate Coordinator

Landing is a loop: check a pull request, tell a Pod to rebase, wait for CI, merge, tell the next
Pods that trunk moved, and repeat. Almost every turn is a status read and a command. Running that
loop on the Captain's Opus session spends the most expensive tier on the cheapest turns, and keeps
the Captain's context full of CI logs. Splitting it out lets the Captain sleep through a run of clean
merges and start only for the ones that need judgment, and once for the review of what landed.

The saving is a hypothesis. Cost per landed pull request is measured with the Captain landing and
with the Coordinator landing before the Coordinator becomes load-bearing.

What keeps a Haiku Coordinator safe is that **it does not judge cleanliness**. Whether a pull request
is clean is a fact computed by one command, `cyberfleet pr check <pr>`, and the Coordinator acts on
its exit status. It never decides that a pull request is "clean enough", and it never reads a verdict
to decide for itself.

## Step by step

### 1. Check the clean bar

The Coordinator reads the ship queue, where each "PR ready" is a thread, and runs the clean bar on
each ready pull request:

```sh
cynapse entry list <ship-queue> --unread
cyberfleet pr check <pr>
```

The command computes four conditions. The first three come from `gh`, the fourth from cynapse:

1. No conflict with trunk.
2. Reviews resolved.
3. CI green on the merged result.
4. The pull request's line of work reported done in its thread on the mission channel, and, where the
   mission has a gate, the gate thread's outcome is a pass.

### 2. Handle the mechanical cases itself

- **A merge conflict, and nothing else.** The Coordinator decides which pull request goes first and
  tells the other Pod to rebase once the first one lands.
- **CI red, caused by this pull request.** The Pod fixes it, as it already does while shepherding.

Each instruction goes in the pull request's queue thread, mentioning the Pod's handle. The mention
wakes the Pod:

```sh
cynapse entry append <queue-thread> --type trunk.moved --ref gh:<org>/<repo>#57 \
  --body "@<pod-handle> trunk moved, rebase"
```

### 3. Land clean work in order

A clean pull request lands only if the Council's delegation covers it. It lands in the order the
blocking links give, so a pull request whose line of work is blocked by another waits for it. The delegation names this
ship's Coordinator, is scoped to the pull requests of the request it answers, is spent per merge, and
sits in the Coordinator's own session as a turn (authority-governance §7, as amended by ADR-0024).
The Coordinator runs speculative CI on the merged result first, as
[merge-backstop-governance](https://github.com/cyberuni/cyberfleet/blob/main/packages/cyberfleet/skills/merge-backstop-governance/SKILL.md)
requires, and merges only on green. Before `gh pr merge` it checks its lease with `service verify`.
After a merge it closes the merged Pod's unit (`cyberlegion unit close`), posts the landing in the
pull request's queue thread, and mentions every other open Pod there that trunk moved. The landing
reaches the mission channel when the Captain posts the outcome. The pull request references its
issue and never closes it: no `Closes #n`.

The Coordinator stays alive while it has pull requests to land. It counts the open pull requests of
each delegated request: up when a Pod opens one, down when it merges or closes. Both are host events,
never inferred. While it waits for a review or CI, it blocks on a command that returns when there is
news (`cynapse entry wait` on the ship queue, `gh pr checks --watch`) rather than polling.

A Coordinator that has no delegation in its own session for a clean pull request holds that merge and
raises a decision-request naming it. That covers a crash, a lease takeover, a Coordinator that exited
between two pull requests of one mission, and a session that can no longer quote your words exactly
from its own turns, for example after compaction. A paraphrase is not a delegation. A headless
Coordinator merges only under a delegation the Council gave before leaving, or under a standing rule.
Otherwise it batches the merge as needs-input.

### 4. Escalate what needs judgment

The Coordinator mentions the Captain in the pull request's queue thread at once for anything that
is not a fact check:

- a review that asks for a change of scope;
- two pull requests that conflict in meaning, not only in text;
- a pull request that stays red after the Pod's fixes, or that a bisect isolated as the culprit;
- a Pod that reports it is stuck.

An escalation needs an answer, so the mention starts the Captain through its lease if no session is
acting as it. The Coordinator joins no mission channel, so the escalation stays where the landing
talk is: in the pull request's queue thread. Two pull requests that conflict in meaning may belong to
different missions, so that escalation goes on the ship queue itself, and the Captain posts the
ruling there and on each mission it concerns.

```sh
cynapse entry append <queue-thread> --type pr.escalation --ref gh:<org>/<repo>#57 \
  --body "@<ship>/captain <what holds it>"
```

### 5. The Captain rules

- **Accept.** The Captain decides the question that held the pull request, for example that the
  review's request is out of scope and becomes a follow-up issue. It gives that direction to the Pod in
  the queue thread, and the pull request goes back through the clean bar. "Accept" does not mean "merge it
  anyway": a red pull request never lands, whoever rules on it.
- **Reject.** The Captain closes the pull request, updates the issue, and replans.
- **Above its leash.** The Captain raises a decision-request to the Council through the Operator.

The ruling goes where it takes effect: its rationale as a comment on the issue, and a one-line
decision entry (ruling, issue, lease generation) on the mission channel it concerns.

### 6. The Coordinator reports once, and the Captain reviews

When the count of open pull requests reaches 0, the Coordinator posts one report of what landed in
the ship queue, mentions the Captain, and exits. The report asks for the Captain's review, so the
mention starts the Captain if none is running. The Coordinator does not report each landing. The
Captain then reviews what merged against its missions and the project as a whole. It decides which missions are
done and closes their issues, reopens an issue when a follow-up the request covers is needed,
calls the frontier command again, and spawns Pods on work that became ready. It posts each mission's
outcome on the mission channel and mentions the Operator, which only wakes it. A follow-up the request
did not cover is a new issue.

This outer loop is judgment, so it runs once per settled queue at the high tier. The cost is that a
queue that keeps refilling delays the review, and work waiting on a landing in the same ship is not
replanned until the queue settles.

## Decisions this page rests on

- **Two leases per ship.** The Coordinator's lease, keyed by its handle (`cyberlegion/coordinator`),
  fences merges. The Captain's lease fences changes to its missions and plan: taking an issue in,
  scope, adding sub-missions, closing, reopening, and writing blocking links. The Coordinator decides
  nothing about the tracker and never writes a blocking link; it runs the mechanics the Captain posts
  to the ship queue.
- **Merge authority.** authority-governance §7 says only the Operator merges under a standing
  delegation. ADR-0024 amends it so the delegation names the ship's Coordinator. The words reach the
  Coordinator as a turn from whoever received them, and nothing holds or re-relays them afterward.
- **Where speculative CI runs.** The main checkout belongs to the Captain, so the Coordinator runs
  merged-result CI and bisection in its own integration worktree, provisioned through the runtime, or
  reads a host merge queue's results.
